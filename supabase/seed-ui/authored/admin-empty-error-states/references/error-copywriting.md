# 错误分类与文案库

错误提示是用户对系统可靠性的直接感受来源。同一句「操作失败」，
换个说法就能让用户从「这破系统」变成「哦，网络问题，我重试一下」。
本文给出完整的分类树与可直接抄的文案模板。

## 一、错误分类树

```
错误
├─ 客户端错误（用户能自己解决）
│   ├─ 400 参数不合法        → 指出哪个参数、应该怎样
│   ├─ 401 未登录 / 登录过期 → 重新登录，保留原 URL
│   ├─ 403 权限不足          → 说明缺什么权限、怎么申请
│   ├─ 404 资源不存在        → 说明可能已删除，给返回出口
│   ├─ 409 冲突              → 说明和什么冲突（如编号已存在）
│   ├─ 422 业务校验失败      → 字段级提示
│   └─ 429 请求过于频繁      → 说明多久后可重试
├─ 服务端错误（用户无能为力，只能重试或报障）
│   ├─ 500 内部错误          → 可重试 + 错误码
│   ├─ 502/504 网关/超时     → 可重试 + 错误码
│   └─ 503 服务不可用        → 提示稍后重试，可给状态页链接
└─ 网络错误（本地问题）
    ├─ 断网                  → 「当前网络已断开」
    ├─ 超时                  → 「请求超时，请重试」
    └─ CORS / DNS            → 提示检查网络，附错误码
```

**判定优先级**：先看有无 `status`，再看 `error.name`（`AbortError` 是主动取消，**不是错误**），
最后归入网络类。`AbortError` 一定要静默忽略，否则切换筛选时会闪一堆错误。

## 二、文案模板

### 2.1 加载类

| 场景 | 标题 | 正文 | 动作 |
| --- | --- | --- | --- |
| 网络断开 | 网络已断开 | 请检查网络连接后重试。 | 重新加载 |
| 请求超时 | 加载超时 | 网络较慢或服务繁忙，请重试。 | 重试 |
| 500 | 加载失败 | 服务暂时不可用，已记录（错误码 5003）。 | 重试 |
| 502/504 | 服务未响应 | 请稍后重试，若持续出现请联系管理员。 | 重试 |
| 401 | 登录已过期 | 请重新登录以继续。 | 重新登录 |
| 403 | 无权访问 | 你没有查看该订单的权限。 | 申请权限 / 返回列表 |
| 404 | 订单不存在 | 该订单不存在或已被删除。 | 返回订单列表 |

### 2.2 提交类

| 场景 | 标题 | 正文 |
| --- | --- | --- |
| 校验失败 | 保存失败 | 有 3 处需要修改，请检查标红字段。 |
| 单字段失败 | （字段级） | 金额必须大于 0。 |
| 409 冲突 | 保存失败 | 订单号 A1024 已存在，请更换。 |
| 429 频繁 | 操作过于频繁 | 请在 30 秒后重试。 |
| 超时（结果未知） | 提交结果未知 | 网络中断，请刷新列表确认是否已保存，避免重复提交。 |
| 无权限 | 无权操作 | 你没有修改该订单的权限，请联系订单负责人。 |

**特别注意「提交超时」**：写操作超时时，结果是不确定的（可能已成功）。
文案必须提示用户**先去确认**，而不是鼓励直接重试 —— 直接重试可能产生重复订单。
后端配合：给写操作加**幂等键**（`Idempotency-Key`），重试也不会重复。

### 2.3 删除类

| 场景 | 文案 |
| --- | --- |
| 确认 | 确定删除订单 1024？删除后不可恢复。 |
| 有关联 | 订单 1024 关联了 3 条退款记录，删除后这些记录也会一并删除。 |
| 被占用 | 无法删除：该客户还有 12 笔未完成订单，请先处理后再删除。 |
| 成功 | 已删除订单 1024（提供「撤销」，保留 5 秒）。 |

## 三、文案写作规则

1. **用用户的语言，不用系统语言**。
   ❌ 「SQLSTATE[23000]: Integrity constraint violation」
   ✅ 「订单号 A1024 已存在，请更换」

2. **给出具体值，不写占位**。
   ❌ 「部分字段填写有误」
   ✅ 「金额必须大于 0，当前为 -5」

3. **区分「重试有用」和「重试没用」**。
   5xx / 网络类可以重试；4xx 校验类重试一百次也一样，文案要引导用户改输入。

4. **错误码必带**。格式 `错误码 5003`，小字放在正文下方，可选中复制。
   用户报障时一句「错误码 5003」胜过三句描述。

5. **不要甩锅**。❌「您输入的数据有误」在系统真的出错时会让用户愤怒。
   不确定是谁的问题时，用中性表述：「保存未成功，请稍后重试」。

6. **不要用感叹号**。❌「操作失败！」会加重负面情绪，用句号。

## 四、错误提示的位置

| 错误类型 | 位置 | 是否自动消失 |
| --- | --- | --- |
| 字段校验 | 字段下方 inline | 否（用户修改后消失） |
| 表单整体校验失败 | 表单顶部汇总 + 滚动到首个错误 | 否 |
| 局部数据块失败 | 该块内 | 否（带重试） |
| 整页加载失败 | 整页居中 | 否（带重试） |
| 操作成功 | 右上角 toast | 是（3 秒） |
| 操作失败（轻） | 右上角 toast | 是（5 秒） |
| 操作失败（重，如提交失败） | 顶部 alert 常驻 | 否 |
| 网络断开 | 顶部常驻条 | 恢复后自动消失 |

**原则**：需要用户**做决定**的错误用常驻；只是**告知**的用 toast。
提交失败需要用户决定「改还是重试」，所以常驻。

## 五、toast 的正确用法

toast 被滥用是后台体验的重灾区。

**该用 toast**：保存成功、复制成功、已删除（带撤销）、轻量的后台任务完成。
**不该用 toast**：表单校验错误、需要重试的加载失败、需要用户阅读的长文案。

- 位置：右上角，距离顶栏 16px，宽度 ≤ 360px。
- 时长：成功 3 秒，失败 5 秒，含撤销的 5 秒。
- 同时最多 3 条，超出排队；**不要**堆满屏幕。
- 必须可手动关闭（hover 时暂停计时）。
- `aria-live="polite"`（成功）/ `assertive`（失败），让读屏能播报。
- 破坏性操作（删除）的 toast 必须带「撤销」，这是廉价的安全网。

## 六、错误边界的兜底

前端渲染崩溃（白屏）也需要兜底：

- 在路由层包一个 Error Boundary，崩溃时显示「页面出错了」+「重试」+「返回首页」+ 错误编号。
- Error Boundary **不能**捕获异步错误和事件处理器错误，异步错误要靠请求层的统一处理。
- 崩溃上报时带上：路由、用户 id、时间、错误堆栈摘要。**不要**上报用户输入的内容（隐私）。
- 给「复制错误信息」按钮，方便用户报障。
