# 深色模式颜色 Token 表与迁移流程

## 一、对比度计算（自己验算用）

```
1. 每个通道 sRGB 值 v（0–1）线性化：
   v <= 0.03928  →  v / 12.92
   v >  0.03928  →  ((v + 0.055) / 1.055) ^ 2.4

2. 相对亮度 L = 0.2126*R + 0.7152*G + 0.0722*B

3. 对比度 = (L_light + 0.05) / (L_dark + 0.05)   （分子是较亮的那个）
```

常用色值在 `#121212` 背景（L = 0.00605）上的对比度：

| 前景色 | L | 对比度 | 判定 |
| --- | --- | --- | --- |
| `#FFFFFF` | 1.000 | 18.7:1 | 过亮，有光晕 |
| `#F5F5F5` | 0.914 | 17.2:1 | 过亮 |
| `#EAEAEA` | 0.827 | 15.6:1 | 上限附近 |
| `#E6E6E6` | 0.791 | 15.0:1 | 推荐正文 |
| `#E0E0E0` | 0.745 | 14.2:1 | 推荐正文 |
| `#CCCCCC` | 0.604 | 11.7:1 | 正文下限 |
| `#A8A8A8` | 0.381 | 8.2:1 | 次要文字 |
| `#8A8A8A` | 0.256 | 5.5:1 | 次要文字下限 |
| `#767676` | 0.181 | 4.1:1 | 仅大字 |
| `#5C5C5C` | 0.107 | 2.8:1 | 不合格 |
| `#404040` | 0.0513 | 1.81:1 | 仅装饰 |

**结论**：深色模式正文用 `#E0E0E0`–`#EAEAEA`，次要文字 `#A0A0A0`–`#B0B0B0`。
不要用 `#FFFFFF`。

## 二、表面层级为什么必须靠边框

同一套算法算表面色：

| 表面 | 色值 | L | 与 `#121212` 对比度 |
| --- | --- | --- | --- |
| 底层 | `#121212` | 0.00605 | — |
| 卡片 | `#1A1A1A` | 0.01096 | 1.12:1 |
| 卡片（更亮） | `#242424` | 0.01760 | 1.22:1 |
| 浮层 | `#2A2A2A` | 0.02217 | 1.34:1 |
| 对话框 | `#333333` | 0.03190 | 1.65:1 |
| 要达 3:1 所需 | `#626262` | 0.1180 | 3.00:1 |

**要满足 WCAG 1.4.11 的 3:1，表面色得亮到 `#626262`** ——
那已经比很多浅色模式的灰底还亮了，深色模式不成立。

所以深色模式的做法是：
- 表面色差用于**暗示**层级（1.1–1.7:1 足够被感知，但不够被"判定"）
- 1px 边框或顶部内高光用于**定义**边界
- 审计时以「边框存在」作为满足 1.4.11 的依据，而不是色差

`rgba(255,255,255,0.08)` 叠在 `#121212` 上约等于 `#212121`，
叠在 `#1A1A1A` 上约等于 `#282828`，对比度约 1.3:1 —— 边框本身也不是高对比的，
但它是一条**清晰的线**，视觉上足够定义边界。

注意深色下的 `--text-on-accent` 是**深色**（`#1A1A1A`），不是白色。
因为 `--accent` 在深色下已经提亮到 `#8AB4F8`，白字在上面只有 2.2:1。
这个 token 最容易漏，漏了就是「深色模式下按钮上的白字看不清」。

## 四、颜色换算：从浅色推导深色

对每个强调色，用 HSL 做机械换算（比凭感觉调色可靠）：

```
深色版 = HSL 的 H 不变
         S 乘 0.80
         L 从原值提亮到 70%–78% 区间
```

例：`#1A73E8` = `hsl(214, 82%, 51%)`
→ `hsl(214, 66%, 76%)` = `#8AB4F8`。

如果用的是 M3 调板，等价规则是「浅色取 tone 40，深色取 tone 80」，
不用自己算 —— 直接用 `TonalPalette.tone(80)` 即可，见 `material-design-3` 技能。

**不要用「亮度取反」**（`255 - v`）来推导深色值。
取反会改变色相：`#1A73E8` 取反得 `#E58C17`，从蓝变橙。

## 五、迁移流程（从只有浅色主题到双主题）

1. **盘点硬编码色值**：`grep -rn "#[0-9a-fA-F]\{3,8\}" src/` 和
   `grep -rn "rgba\?(" src/`，把所有出现位置列出来。
   这一步通常能找出 200–800 处。
2. **归类成 token**：按用途（不是按色值）归类。
   同一个 `#1A1A1A` 如果既做正文又做图标，拆成两个 token。
3. **定义浅色 token 值**：用现值的色值，保证浅色模式**视觉零变化**。
4. **推导深色值**：按上文的换算规则逐个定。灰阶用 `#121212` 起步的层级表，
   强调色用「降饱和 + 提亮」。
5. **替换调用点**：全量替换成 `var(--token)`。这一步之后浅色模式应该完全不变，
   如果变了说明归类有误。
6. **在深色下逐屏走查**，重点看：
   - 有没有漏掉的白底（截图、logo、iframe）
   - 有没有硬编码的黑色文字（在深色下消失）
   - 有没有沿用浅色的阴影（不可见）
   - 有没有沿用浅色的强调色（过曝）
7. **加回归测试**：用 Playwright 在 `colorScheme: 'dark'` 下截图对比，
   把基线图存起来，之后每次改动跑一遍像素 diff。

## 六、常见漏网点

- **第三方组件库**：多数库需要显式传深色主题对象（如 Ant Design 的
  `ConfigProvider theme.algorithm = theme.darkAlgorithm`），不会自动跟随 `prefers-color-scheme`
- **`<iframe>` 内容**：外部嵌入的页面不会跟随宿主主题，需要单独处理或加白底板
- **`<code>` / `<pre>` 的语法高亮**：需要两套 highlight.js / Shiki 主题
- **邮件模板**：Outlook 等客户端不支持 `prefers-color-scheme`，
  要用「只依赖背景色反转也安全」的设计
- **Canvas / WebGL 绘制的内容**：不会自动跟随 CSS 变量，需要重绘
- **`<meta name="theme-color">`**：移动端地址栏颜色，需要手动同步
- **原生导航栏 / 状态栏**：iOS 需要设 `overrideUserInterfaceStyle`，
  Android 需要设 `windowLightStatusBar`
- **favicon 和 PWA 图标**：深色下可能对比不足
- **日期/时间选择器**：`color-scheme: dark` 能解决 Web 端，原生端需要单独配置
