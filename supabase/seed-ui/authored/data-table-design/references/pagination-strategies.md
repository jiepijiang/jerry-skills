# 分页策略：页码分页、游标分页与深分页性能

「分页还是无限滚动」只是表层问题，真正决定成败的是**服务端怎么分页**。
本文给出三种方案的适用场景、接口形态与性能陷阱。

## 一、三种分页方案对照

| 方案 | 接口形态 | 适用 | 致命问题 |
| --- | --- | --- | --- |
| 页码分页 | `?page=3&size=20` | 需要跳页、需要总数、数据变动不频繁 | 深分页慢；数据变动时翻页重复/丢失 |
| 游标分页 | `?after=<cursor>&size=20` | 时间倒序流式数据、数据频繁变动 | 无法跳页、无法显示总页数 |
| 偏移分页 | `?offset=1000&limit=20` | 与页码分页等价 | 同页码分页 |

**默认选页码分页**，除非数据量大到深分页真的慢，或数据变动频繁到页码分页会漏行。

## 二、深分页为什么慢

`LIMIT 20 OFFSET 100000` 要求数据库**先扫描并丢弃 100000 行**，再取 20 行。
100 万行表上这个查询可能几百毫秒到几秒。

**症状**：前几页秒开，翻到第 200 页要转 3 秒，用户以为卡死了。

**解法（按推荐度）**：

1. **限制最大可翻页数**。超过 100 页（2000 条）就不允许跳页，
   引导用户「缩小筛选范围」。这是最实用的一招 —— 没人真的需要翻到第 5000 页，
   他需要的是更精确的筛选。
2. **游标分页**：`WHERE created_at < :last_created_at ORDER BY created_at DESC LIMIT 20`。
   有索引时是 O(log n) 定位 + 顺序扫描 20 行，与页码无关。
3. **延迟关联**：先只查主键 `SELECT id FROM t ORDER BY id LIMIT 20 OFFSET 100000`，
   再用这 20 个 id 回表取字段。减少回表次数。
4. **搜索引擎**（Elasticsearch 等）承担深分页，`search_after` 参数。

## 三、页码分页的接口约定

```json
{
  "list": [ ... ],
  "page": 3,
  "size": 20,
  "total": 3024,
  "totalPages": 152
}
```

- `total` 是分页器显示「共 N 条」的依据。**不要为了省一次 count 查询就不返回** ——
  没有总数用户无法判断「还要翻几页」。
- 如果 count 真的很贵（大表 join），返回 `total: -1` 并在前端显示「共 3000+ 条」，
  不要显示假的精确数字。
- `size` 的合法值限定为 `[20, 50, 100]`，服务端要校验，防止 `size=100000` 打垮数据库。

## 四、数据变动导致的行重复/丢失

用户在翻页过程中，有人往前面插入了新数据，会导致：

- 翻到第 2 页时，第 1 页的最后一条**又出现一次**（重复）。
- 或者某条数据**完全看不到**（丢失）。

**这是页码分页的固有问题**，缓解手段：

1. 排序键加一个**唯一键兜底**：`ORDER BY created_at DESC, id DESC`。
   只用 `created_at` 排序时，同一秒的多条记录顺序不确定，翻页必乱。
2. 后台任务型列表（工单、审核）用「状态 + 游标」而非页码。
3. 在 UI 上不承诺绝对一致性 —— 提供「刷新」按钮，并显示数据更新时间。

## 五、无限滚动的接口与交互

无限滚动**只适合**时间倒序、只往后看的场景（日志、消息、动态）。

- 接口：游标分页。首次请求不带 cursor，返回 `nextCursor`。
- 交互：优先「加载更多」按钮；确要自动加载时，用 `IntersectionObserver` 监听列表底部
  一个 200px 高的哨兵元素，`rootMargin: '200px'` 提前触发。
- 必须有**回到顶部**按钮，长列表滚动后用户回不去。
- 加载失败时，在列表底部显示「加载失败，点击重试」，**不要**把已加载的内容清空。
- **不要**在无限滚动里做「共 N 条」的承诺 —— 用户会数，且你数不准。

## 六、每页条数的选择

| 每页条数 | 适用 |
| --- | --- |
| 10 | 行内含图片/富信息，一屏看不完（极少用） |
| 20 | **默认**，1080p 下半屏，留有滚动余地 |
| 50 | 数据密度高、用户要批量对比 |
| 100 | 导出前的预览、需要一次性看全 |
| 500+ | 不要提供，改为「导出全部」 |

每页条数要持久化到 `localStorage`，并按表名区分 —— 订单表习惯 50，日志表习惯 100，
用同一个值会两边都不舒服。

## 七、跳页输入框的时机

- 页数 ≤ 10：只显示页码按钮，不需要跳页输入框。
- 页数 > 10：显示「跳至 [__] 页」，输入后回车或失焦生效。
- 页数 > 100：跳页输入框 + 提示「也可通过筛选缩小范围」，并考虑限制最大页。
- 跳页输入框要校验：非数字、0、超出总页数时，恢复为当前页并给一个轻微提示，**不要**清空用户输入后什么都不说。

## 八、分页器的最小信息集

一个合格的分页器至少包含：

- 上一页 / 下一页按钮（首页时禁用上一页，末页时禁用下一页，禁用态要视觉可辨）。
- 当前页高亮，页码按钮不超过 7 个（超出用 `…` 省略）。
- 「共 N 条」。
- 每页条数选择器。
- 当前页位置信息（「第 3 / 152 页」），只有页码高亮时用户不知道总量。

**不要**把分页器做成只有 `‹ 1 2 3 … 152 ›` —— 缺了总数和每页条数，
用户无法判断要不要缩小范围。
