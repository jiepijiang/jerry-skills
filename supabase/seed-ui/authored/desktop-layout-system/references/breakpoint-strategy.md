# 断点策略落地：移动优先 vs 桌面优先

主 `SKILL.md` 给的是结论，这份文件给的是**怎么在一个已有项目里换方向**，以及换完之后怎么验证。

## 一、为什么只能选一个方向

CSS 媒体查询没有优先级，只有「后写的覆盖先写的」。当两套方向同时存在：

```css
/* A 区块：桌面优先 */
.card { padding: 24px; }
@media (max-width: 1023.98px) { .card { padding: 16px; } }

/* B 区块：移动优先 */
.card { padding: 16px; }
@media (min-width: 1024px) { .card { padding: 24px; } }
```

最终生效的 `padding` 取决于源码顺序，而不是语义。合并两套写法后，
Review 时无法判断某条规则是否还有效，于是没人敢删任何一条 CSS。

## 二、判定该用哪个方向

| 判据 | 结论 |
| --- | --- |
| 手机流量占比 > 60% | 移动优先 |
| 产品只在桌面浏览器里用（后台、IDE、财务系统） | 桌面优先 |
| 首屏必须出完整信息（营销页） | 移动优先 |
| 页面包含复杂表格 / 多列拖拽 | 桌面优先 |
| 团队没有设计资源，只有一份 Figma 宽屏稿 | 桌面优先（移动优先会因为缺设计而写崩） |

## 三、移动优先的标准写法

```css
/* 基线 = 最窄屏。只写"手机需要什么" */
.nav { display: flex; flex-direction: column; gap: 8px; }

@media (min-width: 640px)  { .nav { flex-direction: row; gap: 16px; } }
@media (min-width: 1024px) { .nav { gap: 24px; } }
@media (min-width: 1280px) { .nav { max-width: 1200px; margin-inline: auto; } }
```

要点：

1. 每个断点只写**从上一档变化的部分**，不要重复写没变的属性。
2. 断点块的顺序必须与数值递增一致，否则覆盖关系出错。
3. 用 `@media` 嵌套写（CSS Nesting 或 SCSS）时，注意编译后顺序仍然是源码顺序。

## 四、桌面优先的标准写法

```css
/* 基线 = 设计稿宽度（通常是 1440）。只写"宽屏需要什么" */
.sidebar { width: 280px; }

@media (max-width: 1279.98px) { .sidebar { width: 240px; } }
@media (max-width: 1023.98px) { .sidebar { width: 200px; } }
```

要点：

1. 断点块顺序必须**递减**。
2. 桌面优先的基线样式会被手机全部下载，若基线里有大图 / 复杂阴影，手机首屏会变慢 ——
   这是桌面优先最实际的代价，需要配合 `@media` 里的资源降级。
3. 桌面优先更容易漏掉「中间档」：从 1440 直接减到 1024，1024–1279 之间的实际表现常常没人测过。

## 五、从一套换到另一套的步骤

1. **冻结**：先提交当前版本，确保可回滚。
2. **清点**：`grep -rn "@media" src/` 导出所有媒体查询，按文件分组。
3. **归类**：每条查询标为 `min-width` 型 / `max-width` 型。
4. **换算**：`max-width: 1023.98px` ⇔ `min-width: 1024px`，边界值必须成对。
5. **逐文件迁移**，一次只改一个文件，改完立刻在 375 / 768 / 1024 / 1440 四档截图。
6. **收敛**：迁移完成后 `grep` 确认只剩一种方向；把断点值抽成变量或 Tailwind screens。
7. **加护栏**：在 CI 里加一条脚本，出现另一种方向的 `@media` 就报错。

```bash
# 护栏示例：项目约定为移动优先，出现 max-width 就失败
if grep -rn "@media[^{]*max-width" src/ --include="*.css" --include="*.scss"; then
  echo "检测到桌面优先媒体查询，本项目约定为移动优先"; exit 1
fi
```

## 六、回归测试清单

迁移或新增断点后，逐条走一遍：

- [ ] 375 / 414 / 768 / 1024 / 1280 / 1440 / 1920 七档截图，无元素重叠
- [ ] 边界宽度 ±2px（如 1023 / 1024 / 1025）三档表现一致，没有闪变
- [ ] 浏览器缩放 125% / 150% 下布局不破（Windows 用户默认就是这个）
- [ ] 系统字体放大到 200% 时文字不溢出容器
- [ ] 页面出现横向滚动条的宽度区间已记录，且是设计允许的
- [ ] 移动优先项目里，基线样式在 375 下不依赖任何媒体查询即可用
- [ ] 桌面优先项目里，1024–1279 中间档已单独截图确认

## 七、断点值为什么是这几个

- `640px`：大屏手机横屏 / 小平板竖屏的分界。
- `1024px`：iPad 横屏与最小桌面窗口的分界，也是「能不能放下双栏」的临界。
- `1280px`：主流笔记本（1366 屏去掉浏览器 chrome 后）的有效宽度。
- `1536px`：外接屏与高 DPI 笔记本的实际工作区起点，也是「可以加侧栏」的临界。

不选 768 / 992 / 1200 的原因：它们对应的是老式设备或某些框架的历史默认值，
在现代设备分布里落不到明确的档位，只会增加测试矩阵而不会改善任何一档的体验。
