# 结算流程

结算（checkout）是整个电商漏斗里**最贵的一段**：
用户已经决定买了，任何摩擦都会直接变成流失。
这一节讲怎么把摩擦降到最低。

## 一、步数设计

### 三步步法（推荐）

```
第 1 步  购物车        确认商品、数量、勾选
第 2 步  填地址与支付    地址 + 配送 + 发票 + 优惠，同页折叠
第 3 步  完成            支付结果 + 订单号 + 后续动作
```

### 为什么不能更多

每一步都会带来一次「页面切换 + 重新定位 + 可能的加载失败」。
行业经验值：每增加一步，流失约 10–20%。
把「发票」单独做一步，为了 5% 的用户牺牲了 95% 的转化，不划算。

### 什么时候可以拆

只有一种情况值得拆步：**地址表单特别复杂**（跨境、需要身份证、需要报关信息）。
此时拆成「收件信息」和「报关信息」两步是合理的，但要在第一步就显示
「共 2 步」，不要让用户在第 1 步之后才发现还有第 2 步。

## 二、第 2 步的字段组织

用折叠区块，默认展开最上面的地址，其余收起：

```html
<section class="ck">
  <div class="ck__block ck__block--open">
    <header><h2>收货地址</h2><button>切换</button></header>
    <div class="ck__address">
      <strong>李维</strong> <span>138****8888</span>
      <p>浙江省杭州市余杭区…… 1 号楼 1801</p>
    </div>
  </div>

  <div class="ck__block">
    <header><h2>配送与发票</h2><span>工作日送达 · 不开票</span></header>
  </div>

  <div class="ck__block">
    <header><h2>商品清单</h2><span>共 3 件，合计 ¥1,197</span></header>
  </div>
</section>
```

要点：

- 收起的区块**标题栏要显示当前值**（`工作日送达 · 不开票`），
  否则用户必须逐个展开才能确认自己填了什么
- 同一时间只允许展开一个区块，避免页面无限拉长
- 地址切换用抽屉，抽屉里默认列出最近使用的 3 个地址

## 三、地址表单字段

### 国内配送必填

| 字段 | 控件 | 校验 |
| --- | --- | --- |
| 收件人 | 文本 | 1–20 字，允许中英文 |
| 手机号 | `inputmode="numeric"` | 11 位，`1[3-9]\d{9}` |
| 省市区 | 三级联动选择器 | 必须选到区/县 |
| 详细地址 | 多行文本 | 5–120 字 |
| 邮编 | 文本（可选） | 6 位数字，不强制 |

### 交互要点

- 手机号输入 **3-4-4 分段显示**（`138 8888 8888`）便于核对
- 省市区用抽屉/弹层选择器，不要用原生 `<select>` 三级联动
- 详细地址用 `<textarea rows="2">`，很多用户地址很长
- **不要在用户还没填完时就标红报错**；在 `blur` 时校验，
  或在点击「保存」时统一校验并滚动到第一个错误项
- 支持**粘贴识别**：用户粘贴一整段地址文本（`李维 13888888888 浙江省…`），
  自动拆分到各字段。这个功能能显著降低移动端填写成本

## 四、优惠与价格明细

价格明细放在提交按钮**上方**，逐行列出：

```
商品合计            ¥1,297
优惠券（满1000-100） −¥100
运费                ¥0
────────────────────────
实付                ¥1,197
```

- 优惠行用负数 + 绿色（或品牌色），与其他行形成对比
- 优惠券选择用抽屉，列出「可用」和「不可用」两组，
  不可用券要写清原因（`还差 ¥203 可用`）
- **不要用弹窗自动推荐优惠券**，会打断结算流程

## 五、提交与支付

- 提交按钮文案：`提交订单`（国内习惯），不要写 `支付`
- 提交后跳转收银台，展示：
  - 订单号
  - 倒计时（通常 15–30 分钟）
  - 支付方式（微信/支付宝/银行卡）
  - 实付金额（大号，加粗）
- 收银台**不要有导航栏返回按钮**（防止误退丢单），只提供「取消订单」
- 支付成功后：展示订单号 + `查看订单` / `继续购物` 两个入口

## 六、异常处理

| 异常 | 处理原则 |
| --- | --- |
| 提交时某商品库存不足 | 保留已填地址，仅高亮冲突商品，让用户改数量后重新提交 |
| 优惠券在提交瞬间失效 | 不阻断提交，改为「已按原价结算」，并给出提示 |
| 支付中断（用户关页面） | 订单保留为「待付款」，首页/订单列表给「继续支付」入口 |
| 重复提交 | 按钮立即 `disabled`，服务端用幂等键去重 |
| 支付成功但页面报错 | 以服务端订单状态为准，刷新后应显示已支付；不要提示「支付失败」 |

## 七、无障碍与可用性

- 所有表单字段有 `<label>` 关联（不要只靠 placeholder）
- 错误提示用 `aria-describedby` 关联到对应输入框
- 必填项用文字标「必填」，不要只用红色星号
- 提交按钮的 loading 状态要有 `aria-busy="true"`
- 整页可以用键盘 Tab 走完，焦点顺序与视觉顺序一致
- 结算页**不做任何轮播、弹窗、倒计时促销**，
  唯一的例外是订单支付倒计时
