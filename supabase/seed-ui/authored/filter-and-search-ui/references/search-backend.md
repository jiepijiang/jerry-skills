# 搜索的后端配合与匹配策略

前端把搜索框做对了，后端用 `LIKE '%关键词%'` 一把梭，照样卡死。本文说清可搜字段、
索引取舍、分词与搜索辅助功能。

## 一、可搜字段必须白名单

不要做「全字段模糊搜索」。三个原因：

1. **性能**：`WHERE a LIKE '%x%' OR b LIKE '%x%' OR ...` 无法走索引，全表扫描。
2. **结果质量**：搜「100」会命中金额 100、ID 含 100、备注里有 100 的，全是噪音。
3. **安全**：全字段搜索可能把不该暴露的字段（内部备注、成本价）也搜出来。

**做法**：每个实体显式声明可搜字段。

```ts
const SEARCHABLE = {
  order:  ['orderNo', 'customerName', 'customerPhone'],
  user:   ['username', 'realName', 'email'],
  ticket: ['title', 'content'],
};
```

前端 `placeholder` 直接由这个列表生成，保证「提示的能搜」和「后端能搜」一致。

## 二、匹配方式与索引的取舍

| 字段类型 | 匹配 | SQL 示例 | 索引 |
| --- | --- | --- | --- |
| 编号类（订单号、手机号） | 前缀 | `LIKE '138%'` | 可用 B-tree |
| 名称类（客户名、标题） | 包含 | `LIKE '%张伟%'` | 不可用，需全文索引 |
| 枚举（状态、类型） | 精确 | `= 'paid'` | 可用 |
| 长文本（备注、内容） | 全文 | `MATCH ... AGAINST` | 需全文索引 / ES |

**关键判断**：
- 如果名称类搜索是**核心功能**（CRM 搜客户、工单搜标题），必须上全文索引或 ES，
  不能靠 `LIKE %x%` 硬扛。
- 如果只是**辅助功能**（偶尔搜一下），且表 < 10 万行，`LIKE %x%` 可以接受，
  但要加超时和结果条数上限。
- 编号类永远用前缀，不要用包含 —— 用户不会从中间记住订单号。

## 三、多关键词处理

用户输入「张 北京」期望的是「名字含张 且 地址含北京」。

```ts
function parseKeywords(raw: string) {
  return raw.trim().split(/\s+/).filter(Boolean).slice(0, 5);  // 最多 5 个词
}
```

- 按空白分词（空格、全角空格、Tab 都要处理）。
- 词之间是 **AND** 关系（缩小范围），不是 OR。
- 限制最多 5 个词，防止用户粘贴一大段文本导致查询爆炸。
- 每个词分别匹配多个可搜字段：`(name LIKE %张% OR phone LIKE %张%) AND (name LIKE %北京% OR ...)`。

## 四、输入归一化

在发请求前统一处理，能显著提升命中率：

| 处理 | 原因 |
| --- | --- |
| `trim()` | 用户粘贴常带首尾空格 |
| 全角转半角 | 中文输入法下数字、字母常是全角（`１３８`） |
| 大小写统一 | 邮箱、英文名大小写不一致 |
| 去连字符（可选） | 手机号 `138-1234-5678` vs `13812345678` |

```ts
const toHalfWidth = (s: string) =>
  s.replace(/[\uFF01-\uFF5E]/g, c => String.fromCharCode(c.charCodeAt(0) - 0xFEE0))
   .replace(/\u3000/g, ' ');
```

## 五、搜索辅助功能

### 1. 搜索历史

- 存在 `localStorage`，按用户 + 实体区分 key。
- 最多存 10 条，去重（重复搜索把它提到最前）。
- 提供单条删除和「清空历史」。
- 隐私敏感场景（HR、财务）不要记录历史。

### 2. 搜索建议（联想）

- 触发阈值：输入 ≥ 2 个字符才开始联想。
- 防抖 200ms，比主搜索快。
- 建议项 ≤ 8 条，超出反而干扰。
- 建议来源：历史记录（优先）+ 热门搜索 + 字段前缀匹配。
- 支持键盘：`↑/↓` 选择、`Enter` 确认、`Esc` 关闭。

### 3. 高亮匹配

```tsx
function Highlight({ text, keywords }: { text: string; keywords: string[] }) {
  if (!keywords.length) return <>{text}</>;
  const esc = text.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');   // 转义
  const re = new RegExp(`(${keywords.map(escapeRe).join('|')})`, 'gi');
  return (
    <>
      {text.split(re).map((part, i) =>
        re.test(part) ? <mark key={i}>{part}</mark> : part
      )}
    </>
  );
}
```

**必须注意**：关键词来自用户输入，直接拼进正则会被注入（`.*` 变通配、`(` 报错），
直接拼进 HTML 会 XSS。**先转义正则元字符，再渲染文本节点（不要用 `dangerouslySetInnerHTML`）**。

## 六、结果排序

搜索结果的排序直接影响「能不能一眼找到」：

1. **精确匹配优先**：搜「张伟」时，名字正好是「张伟」的排在「张伟明」前面。
2. **前缀匹配次之**：`张伟*` 排在 `*张伟*` 前面。
3. **位置靠前优先**：匹配出现在字段开头 > 中间。
4. **业务权重**：如「进行中」的工单排在「已关闭」前面。
5. **兜底**：按时间倒序。

只按时间倒序排搜索结果，会让「张伟」淹没在 500 个「张伟明」里。

## 七、性能兜底

即使做了上面所有事，仍要有兜底：

- **结果上限**：搜索最多返回 500 条，超出提示「结果过多，请补充关键词」。
- **超时**：搜索请求 3 秒超时，超时给「搜索超时，请缩小范围」而不是一直转圈。
- **取消**：新搜索发起时取消上一个未完成的请求（`AbortController`）。
- **缓存**：相同关键词 + 相同条件在 30 秒内命中缓存，避免用户来回改又改回来时重复查询。
- **空关键词**：清空搜索框 = 移除搜索条件，**不是**搜索空字符串。后者在部分后端会变成全表扫描。
